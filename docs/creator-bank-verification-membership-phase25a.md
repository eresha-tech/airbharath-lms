## Provider contract selected

Research was completed against official documentation before adapter implementation (reviewed 9 November 2026):

- [Traditional FAV overview](https://razorpay.com/docs/api/x/account-validation): this API is unavailable in test mode and documented for RazorpayX Lite. Generic test-key suggestions elsewhere do not establish a supported sandbox.
- [Traditional bank validation request](https://razorpay.com/docs/api/x/account-validation/bank-account/): POST `/v1/fund_accounts/validations`, with the source funding identifier as `account_number`, the existing `fund_account.id`, explicit amount, INR and request identity in notes. The beneficiary account number is not the source funding identifier. No undocumented create-idempotency header is assumed.
- [Retrieve validation](https://razorpay.com/docs/api/x/account-validation/fetch-transactions-with-id/) and [enumerate validations](https://razorpay.com/docs/api/x/account-validation/fetch-all-transactions/): authenticated retrieval proves the original fund/contact, bank details, amount and request identity. Enumeration is bounded and paginated; absence never authorizes another POST.
- [Validation webhooks](https://razorpay.com/docs/webhooks/account-validation): both completed and failed notifications are accepted after raw-body HMAC and merchant checks. Persisted hints expedite an independent GET; payload status cannot verify ownership.
- [Composite validation](https://razorpay.com/docs/api/x/composite-account-validation/bank-account): a different contract supports method selection. It is **not implemented in parallel**. Penniless/optimized composite methods are blocked by the selected adapter. A change requires account-specific confirmation and a separate reviewed adapter change; no default fallback can cause a penny drop.
- [Official IFSC toolkit](https://ifsc.razorpay.com/) and [Razorpay IFSC API repository](https://github.com/razorpay/ifsc-api): optional bank/branch lookup. Format or lookup success is not account ownership proof. An unavailable lookup is not invalid-account evidence.

The parser accepts documented `results` and `validation_results` variants conservatively, rejects conflicting variants, and distinguishes transaction status from account status. It records only sanitized result categories and evidence hashes. Bank details remain in the existing encrypted immutable payee record; registered names and raw sensitive provider payloads are not retained or logged. Validation is not complete identity/KYC verification.

## Recovery and approval boundaries

A unique validation intent is stored per immutable payee version and funding scope. The submission marker commits before the only possible POST. A timeout, process crash or lost response therefore cannot trigger another validation payment. Recovery retrieves by the known provider ID or searches for the request UUID in notes, validates the full binding, and never concludes that a missing search result permits another POST. If a crash occurred after the intent marker but before the POST, an operator must trace the original intent; the application cannot prove that it is safe to create a second billable request.

Automatic bank verification requires a completed transaction, an active account and a conservatively normalized name match. Exact normalization allows case, whitespace, common titles and punctuation. Initials, reordered/partial names and missing names require an independent ownership review. A materially different name or definitive invalid result is ineligible. Review does not manufacture a provider match, does not change the original observation and does not bypass mandatory FAV.

Each worker claim has a lease, bounded attempts and backoff. Explicit Admin reconciliation resets only a bounded GET/recovery budget; request identity, submission count, payee version, original contact/fund and prior evidence remain immutable. Signed webhook identity/hash cannot be overwritten. Existing payouts that have already escaped are still independently reconciled even if new validation capability is unavailable; they are not relabelled Paid or retried manually.

## Exact prepaid term rule

Initial purchases retain the historical launch/capture rule. Renewals use `workspace-prepaid-renewal-v1`:

`startsAt = max(verified paidAt, original launch instant, endsAt of every unrefunded fulfilled paid term in the same merchant/mode scope)`

`endsAt = startsAt + purchased calendar months in Asia/Kolkata`, clamped to the last civil day where needed; the end instant is exclusive. Fulfillment takes the shared persisted-user lock. Each captured order creates at most one immutable membership. Early renewal queues another term; it does not edit the earlier one. After expiry, the new term begins at verified capture. Complimentary grant dates and conditions are independent and contribute no prepaid duration. Refunded/held paid orders do not extend a new renewal.

A refunded prior term does not move an already-issued later term or silently bridge a gap. Access selects a presently started unrefunded term, with historical/complimentary access evaluated separately. Future renewals do not grant early access after launch. Refund workflows, invoices, frozen taxes/prices and captured-payment evidence remain unchanged. The checkout waits for its own order to fulfill, so an existing active membership cannot clear a pending renewal request. If a selected plan/price differs from a retained checkout, the screen requires explicit review of that original term and frozen amount before recovering it; it never silently opens the old charge behind a new quote. A newly fulfilled paid term changes the quote hash; a stale concurrent tab must obtain a new quote.

This is one-time prepaid purchasing. There are no mandates, subscriptions, automatic recurring debits, new pricing plans, storage billing, top-ups or mentorship-marketplace expansion.
